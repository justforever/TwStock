## 4. M3 建議

M2 把「籌碼」這條主線打通了，M3 的取捨重點從「補資料」轉向「補正確性與可用性」。建議順序：

| 優先 | 項目 | 理由 |
| --- | --- | --- |
| 1 | **技術債小包**：U-15、U-16、U-17 三項，加 U-13 的 npm 升級 | 都很小但會越拖越髒；U-17 是使用者看得到的數字矛盾，應在有人開始認真看盤之前修掉。U-13 的 `react-router-dom` 破壞性升級要單獨一個任務、單獨一輪審查 |
| 2 | **上櫃除權息（U-10）與上櫃還原價** | 目前上櫃還原 K 線等於原始 K 線，是全專案唯一「畫面看起來正常、數字其實不對」的地方。需要新來源與還原係數重算 |
| 3 | 上櫃借券、上櫃外資持股 | M2 刻意留（D-029）。等 V-10／V-12 回報上櫃端點的真實行為後再做，風險會低很多 |
| 4 | 週 K／月 K、KD／MACD／RSI／布林通道 | 週 K／月 K 要先確認 hypertable 真的建得起來（V-20／V-1）才決定走 continuous aggregate 還是 API 層聚合；技術指標是純前端計算，可與其他任務並行 |
| 5 | ETL 手動重跑（寫入型 API） | M2 完全沒有寫入型端點。真實排程開始跑之後，「某天漏抓要補」會變成高頻操作，目前只能進容器下指令 |
| 6 | 月營收、財報、股利、估值 | 新的資料域，建議等上面的正確性問題收斂後再開 |

### M3 風險

| 風險 | 說明 | 建議對策 |
| --- | --- | --- |
| **真實來源格式與 fixture 不符**（最大） | M2 一口氣新增五個來源、九個端點，全部沒碰過真實回應。上櫃三大法人（S2／S3）與集保 CSV（S9）風險最高 | parser 都有欄位硬檢查，不符會拋 `SourceFormatError` 而非猜測，**不會寫出錯誤數字**。V-9 ～ V-16 逐項回報後可能要改 parser 並更新 fixture，**M3 開工前先把這輪回報做完**，否則 M3 的程式可能建在錯的欄位假設上 |
