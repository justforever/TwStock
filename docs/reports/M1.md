## 5. M2 建議

M1 已經讓「打開個股頁看得到正確的還原 K 線」成立。M2 的主軸建議是**籌碼面 + 副圖**，順便把 M1 留下的缺口補掉：

| 任務 | 內容 | 重點 |
| --- | --- | --- |
| T2-0 | M1 的 Mac 驗證回報收斂（V-1～V-8） | **前置條件**：真實格式若與 fixture 不符，先修 parser 再往下做，否則 M2 疊在未驗證的資料上 |
| T2-1 | 三大法人買賣超（上市／上櫃）schema + parser + loader | 沿用 M1 的 `report.py` 信封與 `job_run`／斷點續傳模式，`etl_job_log` job 名稱比照規格 §4 的命名規則 |
| T2-2 | 融資融券、借券 | 同上；資料量比日 K 小一個量級 |
| T2-3 | 集保分散表（TDCC，週頻） | 唯一非日頻來源，`target_key` 用 `YYYY-WW` |
| T2-4 | 上櫃除權息 + 櫃買指數（補 U-10） | 補完後上櫃還原 K 線才是真的 |
| T2-5 | 週 K／月 K：continuous aggregate（有 TimescaleDB）或 API 端彙總 | 需要 V-1 先確認 hypertable 真的建起來 |
| T2-6 | 前端副圖（法人買賣超／融資券）＋ KD／MACD／RSI（前端計算） | 沿用 D-023：指標不存 DB |
| T2-7 | 維運補強：`scripts/backup.sh`（U-12）、回補收進 CLI（U-9）、相依升級（U-13） | 建議排在 T2-1 之前，成本低、風險最高的是備份 |

### M2 風險

| 風險 | 說明 | 緩解 |
| --- | --- | --- |
| **R-1 來源格式仍是黑盒（延續）** | M2 要碰 TDCC、法人、融券四類新端點，全部只能手寫 fixture；TDCC 是 CSV／HTML 混合，格式比 M1 更雜 | 沿用 M1 做法：欄位硬檢查 + `SourceFormatError`，並在規格裡先寫死「每個新端點都要有 V-x 驗證項」 |
| **R-2 回補量再翻倍** | 法人＋融券＋借券每天各一次請求，5 年再多約 3,600 次請求；TDCC 週頻但檔案大 | 回補框架已可重用（速率限制／斷點續傳）；建議 M2 一開始就把 `backfill` 收進 CLI（U-9），避免又要掛載 `scripts/` |
| **R-3 沒有備份** | 240 萬列日 K 是 3 小時回補的成果，目前只有一個 named volume | T2-7 先做 `backup.sh`，並在 README 寫還原步驟 |
| **R-4 前端效能** | 5Y 全量日 K（約 1,220 根）加三條均線與成交量已接近 Lightweight Charts 單頁舒適上限，再疊副圖會更慢 | 副圖共用同一份資料、以 `setData` 批次更新；必要時改成後端回傳週 K（T2-5） |
| **R-5 還原係數只有上市（U-10）** | 上櫃個股還原價＝原始價，使用者會覺得功能壞了 | T2-4 優先；在此之前前端標註清楚 |
| **R-6 流程再犯（D-027）** | M1 出過一次「審查被跳過 + Coder 自行 commit + 狀態表失真」 | 沿用 D-027：Coder 不得 commit、審查報告只由 Reviewer 寫、沒有審查報告不得標 BLOCKED、commit 標題必須與 diff 相符 |

### 進入 M2 前的前置條件

1. 使用者在 Mac 上完成 §3.1 的 V-1 ～ V-5（compose build/up、hypertable、四個真實端點各跑一次），回報筆數與任何 `SourceFormatError`。
2. 使用者跑一次完整的 5 年回補（V-6），回報耗時、失敗次數與 `daily_price` 實際列數；這也會順便量到本環境估不到的效能與限流行為。
3. 用 `/stock/2330` 抽查還原價（V-7）與隔日的 `/admin/etl`（V-8）。
4. 上述回報之後再開 M2 規格。
