### 缺失

#### 1（major）：`backfill_prices` 的進度行漏印市場別，與規格逐字範例、驗收指令的預期輸出不符

規格 §T1-5-1「進度輸出」與「驗收指令」明文給出的預期輸出都是：

```
[  12/1250] 2021-01-20 TWSE rows=1024 elapsed=00:00:38 eta=01:02:15
...
[   1/   3] 2026-09-16 TWSE rows=4 elapsed=... eta=...
```

以及斷點續傳時：

```
[  12/1250] 2021-01-20 TWSE skip 已完成
```

但實際重跑驗收指令，`scripts/backfill.py price --market TWSE ...` 印出的是：

```
[   1/   3] 2026-09-16 rows=4 elapsed=00:00:00 eta=00:00:00
[   1/   3] 2026-09-16 skip 已完成
```

`market`（`TWSE`）完全沒有出現。原因是 `backfill_prices()`（`etl/twstock_etl/backfill.py` 第 217、232、271、288 行等處）呼叫 `_progress_line()` 時，`name` 參數只傳了 `day.isoformat()`，沒有把 `market` 併入。`backfill_index`／`backfill_exright`／`backfill_calendar` 沒有這個問題（規格對它們的範例本來就不含市場別）。

**影響**：這不是格式美觀問題——README 建議流程第 6、7 步分別對 TWSE、TPEx 各跑一次 `backfill.py price`，使用者若把兩次輸出導到同一個 log 檔案（常見做法，例如 `... 2>&1 | tee backfill.log`）將無法從輸出區分是哪個市場，且與規格明文的驗收指令輸出逐字不符，驗收指令本身即失敗。

#### 2（major）：`interrupted_at` 在 `KeyboardInterrupt` 時記到了「下一個」單位而非「目前」單位，四個 `backfill_*` 都有此問題

規格明文：「捕捉 `KeyboardInterrupt`，設定 `summary.interrupted_at = <目前單位的字串>`」——「目前單位」應為被中斷、尚未完成的那個單位。

但四個函式（`backfill_prices` 第 301-302 行、`backfill_index` 第 444-445 行、`backfill_exright` 第 593-596 行、`backfill_calendar` 第 706-709 行）算法一致，都是：

```python
except KeyboardInterrupt:
    summary.interrupted_at = days[len(days) - (total - i)].isoformat()
```

`i` 是被中斷那個單位的 1-based 索引，`total - i` 是「i 之後尚未處理」的單位數，`len(days) - (total - i)` 化簡等於 `i`，對應到 0-based 的 `days[i]`——也就是**下一個**單位（1-based 第 `i+1` 個），而不是被中斷、實際上尚未完成的第 `i` 個單位。

**實測**（注入 `KeyboardInterrupt` 於第 2 天 `2026-09-17` 處理中）：

```
interrupted_at= 2026-09-18   # 應為 2026-09-17
calls= [2026-09-16, 2026-09-17]
```

`scripts/backfill.py` 會據此印出「已中斷，下次執行會從 2026-09-18 繼續」，但 `2026-09-17` 當下其實被中斷、`etl_job_log` 只留下一列卡在 `running`（`KeyboardInterrupt` 不是 `Exception` 子類別，`job_run()` 的 `except Exception` 不會攔到它，該列狀態永遠不會被改成 `failed`），下次重跑靠 `has_successful_run()` 仍會正確重新處理 `2026-09-17`（不會漏補），**但訊息本身誤導使用者**，也與規格文字明確不符。附帶：`etl_job_log` 會累積永遠卡在 `running` 的孤兒列，`GET /api/etl/jobs`（T1-6）之後若照規格「依 `started_at` 降冪」呈現，會讓 ETL 狀態頁誤顯示「執行中」。

#### 3（major）：`backfill_exright` 離線模式在 `--to` 非月底時，組出的檔名與規格「該月第一天與最後一天」不符，會找不到檔案

規格共同行為第 6 點明文：

> `exright_<YYYYMMDD>_<YYYYMMDD>.json`（**該月第一天與最後一天**），例 `exright_20260901_20260930.json`

但 `backfill_exright()`（`etl/twstock_etl/backfill.py` 第 466-483 行）用

```python
months = [(s, min(e, end)) for s, e in months]
```

把每個月份的結束日 clip 到整體 `end`，最後一個（通常是唯一真正會用到的）月份若 `end` 不是月底，就會用 clip 後的日期組檔名，而非「該月最後一天」。

**實測**：`backfill_exright(engine, date(2026,9,1), date(2026,9,18), ...)`（`--to 2026-09-18`，正是規格 CLI 範例與 README 建議流程步驟 8 使用的日期）：

```
[   1/   1] 20260901-20260918 FAIL 檔案不存在：etl/tests/fixtures/exright_20260901_20260918.json
```

而規格要求／既有 fixture 檔名其實是 `exright_20260901_20260930.json`。也就是說，**規格自己給的 README 建議流程第 8 步，用離線 fixture 實際跑起來會失敗**，因為 `--to` 用的是「今天」而非月底。這不是邊界情境，是最常見的呼叫方式（`--to` 幾乎不會剛好是月底）。

同一個 bug 也會影響上線模式：`load_adj_factors()` 的 `target_key`（進而 `etl_job_log` 記錄）會是 clip 後的區間（如 `20260901-20260918`），而非規格 §4 job 名稱表期待的「以區間為單位」的整月語意，下次排程若改用完整月份區間呼叫，`has_successful_run()` 會因 `target_key` 不同而判斷為「未完成」，重複打一次官方端點（違反「回補與排程共用同一組斷點」的設計精神，雖然規格只在 `daily_price_*` 明文要求「每日與回補共用同一個名稱」，但這裡的不一致仍值得在下一輪一併修掉）。

### 未構成 blocker 的觀察（供下一輪參考，非必改）

- `etl/tests/test_etl_backfill.py::test_backfill_prices_missing_source_file` 用整個不存在的目錄（3 天全部找不到檔案），與規格「§3 測試」要求的「`source_dir` 少一個檔案 → `failed == 1`，其他兩天仍成功」不是同一個情境，沒有測到「部分成功、部分失敗」的路徑，建議下一輪補測。
- `_progress_line()` 等格式化函式本身沒有 print，實際 `print(..., file=options.out, flush=True)` 都直接寫在四個 `backfill_*` 函式本體裡，而不是集中在一個獨立的「進度輸出函式」；規範原文允許 `backfill.py` 的「進度輸出函式」print，本次寫法在精神上仍算符合（進度輸出仍侷限在該模組），但下一輪如果要順手重構成單一 `_emit_progress()` 之類的函式會更乾淨、也更容易把缺失 1 的市場別一併補上。

### 結論

**REQUEST_CHANGES**。三個 major 缺失（進度行漏市場別、`interrupted_at` 中斷點算錯、`exright` 離線檔名在非月底 `--to` 時對不上）都會讓規格明文的驗收指令或 README 建議流程之一實際執行失敗或產出誤導訊息，不是規格本身有誤或環境限制，屬程式問題，退回 Coder 修正。狀態表維持 `IN_REVIEW`（依 D-027，`BLOCKED` 需等本審查報告——即本文件——存在後才能標，故下一輪由 Architect／Coder 視流程需要改為 `BLOCKED` 或直接修正）。

### 新缺失

#### 4（major，新回歸）：`backfill_exright` 的斷點續傳檢查（外層 `target_key`）與 `load_adj_factors` 實際寫入 `etl_job_log` 的 `target_key` 不一致，導致同一個非月底 `--to` 重跑時永遠判定「未完成」，每次都重新發送請求（不消耗跳過、且違反「已完成不消耗速率限制」）

本輪修正把 `backfill_exright()`（`etl/twstock_etl/backfill.py` 第 480-497 行附近）拆成兩個日期：`month_end_original`（該月最後一天，用於離線檔名與外層 `has_successful_run` 檢查的 `target_key`）與 `month_end_clipped`（`min(該月最後一天, end)`，用於實際呼叫 `load_adj_factors(engine, month_start, month_end_clipped, ...)`）。

但 `load_adj_factors()`（`etl/twstock_etl/jobs.py` 第 512 行）內部自己算的 `target_key` 是 `f"{start:%Y%m%d}-{end:%Y%m%d}"`，用的是**它實際收到的參數**，也就是 `month_end_clipped`——不是 `month_end_original`。也就是說：

- `backfill_exright` 外層檢查／寫入 `interrupted_at`／進度行印的 `target_key`：`20260901-20260930`（完整月）。
- `load_adj_factors` 真正寫進 `etl_job_log` 的 `target_key`：`20260901-20260918`（clip 過的，等於 `--to`）。

兩者只有在 `--to` 剛好是月底時才會相同；`--to` 非月底時（也就是規格自己在 README 建議流程第 8 步、CLI usage 範例用的日期，幾乎是最常見的呼叫方式）兩者永遠不同。

**實測**（乾淨 DB，同一個 `--from 2026-09-01 --to 2026-09-18`，`--source-dir` 指向 fixtures，連續呼叫兩次 `backfill_exright`，不加 `--force`）：

```
run1: [   1/   1] 20260901-20260930 rows=2 ...   完成 1／跳過 0／失敗 0，共寫入 2 筆
run2: [   1/   1] 20260901-20260930 rows=0 ...   完成 1／跳過 0／失敗 0，共寫入 0 筆
```

`run2` 的 `rows=0` 顯示 `load_adj_factors` 內部自己的 `has_successful_run(target_key="20260901-20260918")` 有正確擋下重複寫入（沒有重複 upsert），**但外層 `backfill_exright` 完全沒有偵測到「已完成」**：

- 外層印的是 `done`（不是規格要求的 `skip 已完成`），`summary.done` 又多算了 1 筆，`summary.skipped` 永遠是 0——統計數字錯誤，且與規格共同行為第 1 點「`has_successful_run(...)` → 印 `skip` 並計入 `skipped`」不符。
- 更嚴重：外層在真正發 HTTP（非離線模式）時，`limiter.wait()` 在呼叫 `load_adj_factors` **之前**就執行（見第 528-529 行），也就是說即使該月早已回補過，只要 `--to` 不是月底，**每次重跑都會照樣睡滿 `--sleep` 秒、且照樣對官方端點發一次 HTTP 請求**，才在 `load_adj_factors` 內部被擋下——完全違反規格「已完成……不消耗速率限制」的要求，且會對外部端點造成不必要的重複請求（規格明文最擔心的就是這件事：TPEx 端點「本里程碑風險最高」）。
- 這不是規格本身的模糊地帶：規格 §4 job 名稱表對 `adj_factor_twse` 只定義了一組 `target_key` 語意（「以區間為單位」），`backfill_exright` 自己算的 `target_key` 應該與它實際傳給 `load_adj_factors()` 的 `(start, end)` 一致，而不是各用各的日期。修正方式：外層 `has_successful_run` 檢查、進度行、`interrupted_at` 全部改用 `month_end_clipped` 組 `target_key`（與 `load_adj_factors` 內部一致）；離線模式的**檔名**則繼續用 `month_end_original`（規格明文「該月第一天與最後一天」，這部分本輪修法沒錯，不用動）。

**這是本輪修正的回歸**：第 1 輪原始程式碼 `target_key` 全部用 clip 過的日期（`months = [(s, min(e, end)) for s, e in months]`），外層與 `load_adj_factors` 內部本來是一致的（只是離線檔名跟著錯，即第 1 輪缺失 3）；本輪修正只改了「用哪個日期組檔名」，卻連帶把外層 `has_successful_run` 檢查／`target_key` 也一併換成完整月，讓原本一致的兩處變得不一致，等於用一個新 bug 換掉了一個舊 bug。

### 未構成 blocker 的觀察（供下一輪參考，非必改）

- 第 1 輪「未構成 blocker」的兩點（`test_backfill_prices_missing_source_file` 情境不完整、進度輸出未集中成單一函式）本輪未動，仍待下一輪視情況處理，非本輪必改項。

### 結論

**REQUEST_CHANGES**。新缺失 4（`backfill_exright` 外層斷點續傳的 `target_key` 與 `load_adj_factors` 實際寫入的 `target_key` 不一致，導致非月底 `--to` 時永遠判定未完成、每次重跑都重新發請求）是程式問題，不是規格或環境限制，退回 Coder 修正。第 1 輪三個 major 缺失（進度行漏市場別、`interrupted_at` 算錯、離線檔名）均已確認修正，下一輪只需處理缺失 4，且修法明確（`has_successful_run` 檢查與 `target_key` 一律改用 `month_end_clipped`，離線檔名維持用 `month_end_original`）。狀態表維持 `IN_REVIEW` / `BLOCKED`（依實際流程狀態，不改為 `DONE`）。
