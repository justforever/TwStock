### ETL 冪等性

- 本任務本身不寫入資料庫（唯讀 API），冪等性檢查落在讀取邏輯是否會因重覆資料而錯亂：
  `fetch_prices`／`fetch_index_prices` 皆以 `(stock_id/index_id, trade_date)` 主鍵讀取，
  不會因為 ETL 重跑（`ON CONFLICT DO UPDATE`，T1-3 已核准）而產生重複列。
- 交叉驗證 T1-5 的斷點續傳在 API 讀出的資料上沒有副作用（重跑後 `count`、`close` 值不變，與第一次 backfill 後一致）。

### 問題清單

1. **[minor] `api/tests/test_api_adjust.py:87`**（`test_apply_adjustment_basic`）：
   ```python
   assert result[0]["high"] == Decimal("995.0000") if Decimal("1005.0") * Decimal("0.99") == Decimal("995.0000") else Decimal("994.9500")
   ```
   三元運算子優先權問題：這行實際上是
   `assert (result[0]["high"] == Decimal("995.0000")) if <条件為 False> else Decimal("994.9500")`，
   於是永遠執行 `else` 分支、`assert Decimal("994.9500")`（非零 Decimal 恆真），**完全沒有比對 `result[0]["high"]` 的實際值**，形同沒測。
   本輪審查已用獨立手算（`1005.0000 * 0.99 = 994.9500`）與 `test_get_prices_adjusted_open_high_low`（走 API 層、真的斷言 `pytest.approx`）交叉確認 `adjust.py` 的計算正確，因此**不影響本輪 APPROVE 結論**，但建議 Coder 下一個任務接觸到這個檔案時順手修成：
   ```python
   assert result[0]["high"] == Decimal("994.9500")
   ```
   （或乾脆用 `pytest.approx`／直接手算好的常數，不要在 assert 裡寫條件式。）
