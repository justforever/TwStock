### Blocker

1. **`etl/twstock_etl/loaders/chip.py`：四個 upsert 函式的 `written` 計數全部錯誤（回傳 -1）**
   `upsert_institutional` / `upsert_margin` / `upsert_sbl` / `upsert_foreign_holding` 都用
   `result = conn.execute(stmt); total += result.rowcount` 累計批次寫入筆數。
   規格明講「骨架完全比照 `loaders/price.py` 的 `upsert_daily_prices`」，但該函式是用
   `total += len(batch)`，**沒有用 `rowcount`**。psycopg 對多列
   `INSERT ... ON CONFLICT DO UPDATE` 回傳的 `rowcount` 是 `-1`（無法得知筆數），
   導致 `PriceUpsertResult.written` 永遠是 `-1`。

   實測（跑規格「驗收指令」原文的四個 `load-chip` / `backfill chip` 指令）：

   ```
   完成 3／跳過 0／失敗 0，共寫入 -3 筆，耗時 00:00:00
   loaded kind=margin market=TWSE date=2026-09-18 rows=-1 skipped_unknown=1
   loaded kind=sbl market=TWSE date=2026-09-18 rows=-1 skipped_unknown=1
   loaded kind=foreign market=TWSE date=2026-09-18 rows=-1 skipped_unknown=1
   ```
   規格預期是 `共寫入 9 筆`、`rows=3`、`rows=2`、`rows=2`。這不是隨機誤差，而是每次呼叫都
   固定回 `-1`；連帶把 `etl_job_log.rows` 也寫成 `-1`（用
   `SELECT job_name, rows FROM etl_job_log` 實測確認），污染營運可觀測性，也會讓
   T2-7 `verify_chips.py`／`m2_verify.sh` 若比對筆數就會失敗。

   註：資料本身寫得對——同一次跑完後查 `institutional_daily` / `margin_daily`，
   `foreign_net`／`total_net`／`margin_balance`／`short_balance`／`sbl_sell`／`sbl_balance`
   數值都與規格 §驗收指令 完全吻合（5000000/8000000/12000000、13500000、
   20200000/1090000/300000/4500000）。問題**只在回傳的筆數統計**，但這個統計是
   CLI 輸出、`etl_job_log.rows`、回補摘要都在用的欄位，屬於功能缺陷，非文字瑕疵。

   **建議修法**：比照 `upsert_daily_prices`，四個函式改成 `total += len(batch)`（批次內已用
   `on_conflict_do_update` 保證每筆都會被寫入或更新，筆數等於這批 filtered_records 的長度）。

2. **`etl/tests/test_etl_chip_jobs.py` 匯入路徑錯誤，整個測試檔在 collection 階段就失敗，
   導致 `pytest -rs`（不限定路徑）直接中斷、一個測試都不會跑**
   ```python
   from twstock_etl.models import InstitutionalRecord, ChipJobResult
   ```
   `ChipJobResult` 是定義在 `twstock_etl/jobs.py`（規格 §3），不在 `models.py`。
   實測：
   ```
   ImportError: cannot import name 'ChipJobResult' from 'twstock_etl.models'
   Interrupted: 1 error during collection
   ```
   同一個 repo 內其他新檔案（`test_etl_cli.py`、`test_etl_scheduler.py`）都正確從
   `twstock_etl.jobs` 匯入 `ChipJobResult`，只有這個檔案匯入錯誤模組，顯示是筆誤而非設計判斷。

3. **`etl/tests/test_etl_chip_backfill.py` 用不存在的 `BackfillOptions` 欄位與匯入路徑，4 個測試裡 3 個直接 `TypeError`，1 個 `ImportError`**
   - `BackfillOptions(dry_run=..., rate_limit_days=0, offline_dir=None)`：
     `BackfillOptions` 實際欄位是 `sleep_seconds` / `source_dir`（見
     `etl/twstock_etl/backfill.py`），沒有 `rate_limit_days` / `offline_dir`，
     3 個測試（`test_backfill_chip_invalid_combo`、`test_backfill_chip_dry_run`、
     `test_backfill_chip_error_handling`）建構 `BackfillOptions` 那一行就
     `TypeError: unexpected keyword argument`。
   - `from twstock_etl.backfill import ChipJobResult`：`ChipJobResult` 定義在
     `jobs.py`，`backfill.py` 只是 `from twstock_etl.jobs import (..., load_chip_daily)`，
     並未 re-export `ChipJobResult`，`test_backfill_chip_basic` 因此 `ImportError`。

   實測：`etl/tests/test_etl_chip_backfill.py` 4 個測試全部失敗。

### Major

4. **測試內容與規格 §8「測試」清單嚴重不符，關鍵案例（含本輪特別要求檢查的
   D-037 部分 upsert 隔離）完全沒有測到**
   - 規格第 4、5 點明確要求驗證「借券只更新 `sbl_*` 兩欄，不動融資融券欄位」、
     「借券可以先於融資融券寫入，兩邊互不覆蓋」（D-037 的核心行為），
     但 `test_etl_chip_loaders.py` 裡完全沒有這兩個案例——每個 `upsert_*` 測試都是
     各自獨立塞資料、互不交互，沒有任何一個測試在同一個 `(stock_id, trade_date)`
     上先後呼叫 `upsert_margin` 再 `upsert_sbl`（或反過來）並比對欄位互不覆蓋。
     這正是 T2-6 最容易犯錯、也是本輪審查被要求特別檢查的地方，目前完全沒有回歸保護。
   - 規格要求用真實 fixture（`TWSE_institutional_20260918.json`、
     `TPEx_institutional_20260918.json` 等）驗證 parser→loader 整條路徑與精確筆數
     （例如「法人寫入三筆未知一筆」「上櫃法人載入 rows==2 skipped_unknown==1」），
     現有測試改用手寫的 `InstitutionalRecord` / `MarginRecord` 假資料，
     完全繞過了 T2-4／T2-5 parser 的實際輸出，等於沒有測到 `chip_sources.py`
     登錄表接線是否正確（`fetch`／`parse` 有沒有配對錯誤市場或錯誤 kind）。
   - 規格第 7–13 點要求的：四種 kind 都能經 `load_chip_daily` 載入、
     `etl_job_log.job_name` 集合核對、非開市日 skip、`ValueError` 時
     `etl_job_log` 沒有新增列、上櫃法人載入——`test_etl_chip_jobs.py` 一個都沒有
     （該檔案的 4 個測試是完全不同的內容，且如 Blocker #2 所述根本無法執行）。
   - 規格第 14–17 點要求的「檔案不存在算一次失敗」「進度行格式」——
     `test_etl_chip_backfill.py` 也沒有覆蓋（該檔的 4 個測試同樣是另一套內容，
     且如 Blocker #3 所述 3/4 直接報錯）。

   總結：目前的三個新測試檔案基本上是各自重新設計了一套簡化測試，
   而非落實規格逐條列出的驗收案例；即使修好 Blocker #2／#3 的匯入問題，
   規格要求的關鍵案例仍然缺漏。
